Content Loading Pipeline

Manifest, Storage Roots, and Cache Layers

Manifest-driven project layout

The engine keeps every asset and map definition out of the binary by relying on manifest.json, which is read and written via manifest::load_manifest()/manifest::save_manifest() in ENGINE/core/manifest/manifest_loader.cpp. The loader guarantees the folder structure under project/SRC, so the engine can later discover assets, loading screens, and other shared content without manual setup.

Storage roots and regenerated caches

While SRC/assets and the manifest store the human-authored content, the runnable engine resolves a per-map content_root (defaulting to content/<map>) during MainApp::setup(). Generated frames live inside the cache/ hierarchy, so the SDL renderer reuses scaled/filtered textures across maps instead of re-encoding them every launch. The cache is refreshed by tools/asset_tool.py and tools/light_tool.py whenever needs_rebuild flags in the manifest are set, while RebuildQueueCoordinator (invoked from main()) forwards queued work to those scripts before running the game.

Asset Library and Texture Pooling

AssetInfo metadata and shared caching

AssetLibrary synchronizes manifest.json with discovered folders under SRC/assets (see ENGINE/asset/asset_library.cpp), creating AssetInfo instances that capture animation groups, light sources, spawn settings, and shading hints. These AssetInfo objects hold texture paths and animation children, so AssetLoader can instantiate assets without re-reading JSON on every spawn. Once the SDL renderer is ready, either the shared asset library or the per-map loader preloads animation variants via AssetInfo::loadAnimations(), ensuring there is a pool of GPU-backed frames cached before assets are registered in the world grid.

Python-powered texture pipelines

tools/asset_tool.py is the explicit texture pipeline: it reads the manifest, inspects source frames inside SRC/assets/<asset>, scales them down to fixed variants, applies the configured fg/bg effects, and stores the resulting PNGs in cache/<asset>. A similar tools/light_tool.py rebuilds per-asset light masks when lighting_info[].needs_rebuild is true. Both tools honor the manifest metadata so the runtime never has to run heavyweight image effects; it simply reads prepared scale steps and light textures from cache/.

Map, Room, and Trail Construction

Manifest map layers, rooms, and trails

The manifest’s maps entry comprises map_layers, map_assets_data, map_boundary_data, rooms_data, trails_data, and map_grid_settings. AssetLoader::load_from_manifest() populates these fields and deduces map_radius, layer_radii, and slice-specific spawn controls. Missing layers trigger a synthesized spawn room so the engine always has a playable area.

Room geometry, spawn groups, and trails

GenerateRooms uses the parsed layers to produce Room instances, each with its Area geometry, spawn groups, and inherits/spawns rules. SpawnContext (with AssetSpawnPlanner) samples the rooms and trails, respects spacing filters, and calls AssetLoader::spawnAsset to create Asset objects that are later finalized. Trails share the same infrastructure but reuse trail-specific Area definitions to control spawn and visibility.

Grid settings and caching

Each map provides MapGridSettings (resolution, chunk size, etc.), which guide AssetLoader::createAssets() when it initializes the world::WorldGrid chunk resolution and calls grid::chunk helpers to build z-indexed tiles. Room-specific MapGridSettings also feed the Asset spawn helpers so that collision, depth sorting, and camera culling stay consistent with the layout.

Scene & Asset Structure

World Grid, Chunks, and Rooms

The world::WorldGrid keeps assets bucketed into chunks and grid points so spatial queries, collision checks, and active-asset selection stay fast. Each chunk is created lazily via ensure_chunk_from_world(), and assets register via create_asset_at_point(). The grid tracks both chunk residency and per-point occupancy, enabling Assets::update_active_assets() to restrict updates to visible regions.

Asset metadata, child assets, and tiling

An Asset instance owns a shared AssetInfo, spawn identifiers, animation runtime, and optional tiling metadata. AssetInfo describes light sources, shadow masks, animation children, and spawn groups, and the runtime uses this metadata for shading, lighting, and relationship wiring. Child assets and timeline entries attach via Asset::animation_children(), while Asset::TilingInfo lets large rooms re-use an asset across a coverage rect.

Animation runtime and custom controllers

The animation stack centers on AnimationRuntime and AnimationUpdate. AnimationUpdate exposes path planning helpers like auto_move(), move(), and set_animation() to both default and custom controllers. AnimationRuntime steps the animation frames, evaluates root motion against the grid, and advances child timelines while the MovementPlanExecutor and GetBestPath helpers keep checkpoints sane. Custom logic lives in factories under ENGINE/animation_update/custom_controllers and implements the AssetController interface; controllers are chosen via ControllerFactory::create_by_key() when the manifest attaches a custom_controller_key to an asset.

Runtime Flow & Rendering

Main loop, input, and asset updates

MainApp::game_loop() ties everything together at 60 FPS: SDL events feed Input, Assets::handle_sdl_event(), and, if a player exists, the controller system. Assets::update() then advances Asset::update(), which applies controller logic, runs AnimationRuntime::update(), and marks render packages dirty when animations or lighting change. During setup MainApp also initializes audio via AudioEngine::instance().init() and decides whether to start in Dev Mode when no player asset appears.

Screen grid, camera, and lighting

WarpedScreenGrid maintains the screen-oriented camera: it rewrites map coordinates to screen space, smooths zoom/pan via TransformSmoothingState, and enforces realism_settings (e.g., horizon fade, parallax, render quality). The grid rebuilds itself against the WorldGrid each frame so grid_point_for_asset() stays accurate, and Assets exposes the camera via getView() together with lighting toggles such as map light overlays, dark mask, and depth effects. LightMap and MapLightPanel coordinate lighting updates that feed both the renderer and the Dev Mode UI.

Rendering pipeline and composite packages

SceneRenderer orchestrates the drawing pass. It clears the screen, renders background fog/sky textures, and delegates to CompositeAssetRenderer to build an asset’s render_package. A composite package collects scaled textures, child attachments, and lighting masks in the desired draw order; CompositeAssetRenderer::regenerate_package() also handles scene mask lights and flickering intensity from LightFlickerCalculator. After assembling packages, the renderer sorts assets by depth, draws map lighting, and optionally blits depth cues, dark masks, and postprocessing textures.

Auxiliary runtime systems

Beyond assets and rendering, Assets tracks selection/highlight state, persists map_info_json changes, and exposes helpers for room config panels, asset library popups, and quick task notifications. Asset::set_hidden() and collectDistantAssets() in AssetLoader gate assets far from the camera, while RebuildQueueCoordinator ensures rebuild scripts finish before the main loop runs; DevControls and MapLightPanel rely on this to edit and persist data safely.

Dev Mode Toolkit

Dev Mode flips the engine into an editor-ready state, reduces render quality for responsiveness, and wires DevControls to ManifestStore so user edits persist back to manifest.json. The toolkit is reachable via Ctrl+D (or by launching a map that has no player asset), and it keeps dev-specific layout filters in dev_mode_settings.json while streaming changes into the shared AssetLibrary.
